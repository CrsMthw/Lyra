# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

_A discovery release — Lyra gains a layer that shows you something without being asked: an opt-in "For you" band, saved albums and followed artists in the Library, and a listening-stats screen. Podcasts arrive (a Shows filter, a Shows search tab, show detail and episode playback across every player surface), playlists get multi-select removal with server-confirmed counts, Search moves to tabs with per-type paging and remembers more, the mini player reaches every browse screen, and the pop-out panel gets the circle visualizer. Plus a toolchain upgrade, a warning-free compile, and a motion/touch fix pass that makes back navigation behave consistently everywhere._

### Added
- **"For you" band on the Library — opt-in, default OFF** — a *Jump back in* row (recently-played contexts, de-duped by uri: playlist / Liked Songs / album / artist tiles; playlist contexts resolve their name and art against your library list, Liked Songs renders its gradient tile) and an *On repeat* row (short-term top tracks; tap plays from that index with the rest queued, touch-and-hold opens the song menu). Built on `GET me/player/recently-played` + `me/top/{tracks,artists}`, and persisted in `LibraryCache` (a nullable `ForYouCacheData`, for Gson `Unsafe`-alloc safety) so it paints instantly from cache. **Algorithmic resurfacing is the kind of Spotify bloat Lyra exists to escape, so the band is behind a "For you band" toggle in Settings → Lyra and ships off**; while off it is hidden *and* its API calls are skipped entirely (the loader reads the persisted flag directly, avoiding a start-up ordering race with the state mirror). Flipping it on mid-session fires the skipped fetch so the band fills in without a manual refresh.
- **Library content filter — Playlists / Albums / Artists** — a connected M3 `ButtonGroup` at the top of the browser switches between your playlists, your **saved albums** (`me/albums`, offset-paged) and your **followed artists** (`me/following`, cursor-paged). Each list is fetched once per session on the first switch to it and cached in `LibraryCacheData` so it paints instantly next launch; rows navigate to the existing Album / Artist detail screens.
- **Listening-stats screen ("Wrapped-lite")** — a new `Screen.Stats`, entered from an Insights action on the Library top bar: top artists as a rank-badged circle row and top tracks as a ranked tap-to-play list (touch-and-hold opens the song menu), behind a connected **4 weeks / 6 months / all time** picker. Results are cached in memory per range, so switching ranges is instant. (Album-palette tinting deferred — plain M3 colours for v1.)
- **Add to queue** — an "Add to queue" row in the song touch-and-hold menu, via `POST /me/player/queue`. The row disables while the call is in flight, toasts the result, then dismisses.
- **Share track** — a "Share" row in the same menu (`Intent.ACTION_SEND` with the `open.spotify.com` URL, matching the player's existing share button).
- **Save album / follow artist** — a heart toggle in the top-right pill of the Album and Artist detail screens (single-pane and two-pane), through the unified `me/library` save / remove / contains. Optimistic with revert on failure, and it surgically updates the cached Albums / Artists filter lists (a cache revision ping makes the Library re-sync).
- **Predictive back in the Library track list** — backing out of a playlist or Liked Songs in single-pane is now **gesture-driven**: the pane swap and the card↔hero container transform seek with your finger and unwind if you release early, instead of firing as a fixed animation after the gesture commits. The swap is not a nav destination (both panes live in one screen), so it is driven by a `SeekableTransitionState` the same way `NavHost` does it internally. The transition's state is the **pane identity** (playlist id / `"liked"` / `null`), not the whole UI state — `SeekableTransitionState` compares targets with `equals`, so animating over the state object would make every ordinary emission (a page of tracks arriving, a refresh landing) a *new target* that resets the gesture's progress and restarts the swap mid-flight. Partially delivers the planned predictive-back polish pass; the search-bar morph is still to do.
- **Multi-select removal in owned playlists** — removing several songs no longer means one long-press-and-menu round trip per track. A selection mode in the playlist detail batch-removes every checked row in a *single* API call. Two doors into the same mode, both offered on exactly the condition that already shows "Remove from <playlist>" — the song lives in a playlist you own, so **Liked Songs and followed playlists show no Select affordance at all**: a **"Select" row in the song touch-and-hold menu** (which enters the mode with that song already checked) and **"Select songs" in the detail's ⋮ menu**, discoverable without a long-press. In the mode a tap (or a long-press — no sheet) checks a row and ticks, the album art doubles as the checkbox so the row never shifts, the app bar crossfades to a contextual `✕  N selected  ⌫` bar, and the hero's Play/Shuffle are suspended because a tap in the list is now a check. Back exits the mode without leaving the playlist — and in single-pane it takes precedence over the predictive-back pane swap, so cancelling a selection can never start dragging the playlist away. Works in single-pane and in the two-/three-pane right pane. Removal sends the whole selection in one `RemoveItemsRequest` (chunked past the API's 100-item cap), drops the rows immediately, and then **confirms the count against the server** — the playlist's real total is re-read once, shortly after the edit, and written to the hero, to both browser cards and to the cache together, so the two numbers can never disagree and the Library view needs no manual refresh; on failure the rows stay and an error dialog explains why — and a removal that only *partly* went through (a dropped connection or rate-limit mid-batch) drops the rows that were actually removed and keeps the rest selected for a retry, instead of claiming nothing was removed while the playlist is already shorter. The list stays anchored on the song you were looking at when rows above it are removed (rows are keyed on the track's uri plus an occurrence ordinal, never the list index). Pull-to-refresh is disabled while selecting, a refresh that lands mid-selection exits the mode, and an edit made elsewhere (the player's add-to-playlist sheet, the song menu on another screen) narrows the selection to what is still in the list rather than leaving it pointing at songs that are gone. The remove action is a plain trash icon, and removing **two or more** checked songs asks for confirmation first (a single one still goes straight through). Unchecked rows show a bordered badge on the art that stays visible over dark artwork. Back while the pop-out player is open closes the panel first — the two back handlers are now mutually exclusive on shared state rather than relying on registration order, which unfolding could reverse. This supersedes the planned swipe-to-remove, which stays rejected.
- **Search results are split by type, and each type pages on its own** — results used to be one list of stacked sections (a horizontal row of artists, then tracks, then albums), which meant that as tracks paged in, the Albums section drifted further down and became genuinely hard to reach. **Tracks / Albums / Artists** tabs (a Material 3 primary tab row, full width under the search bar) now split the results, and each type is its own list with its own scroll position, so switching back to a tab lands where you left it; the lists are pages, so the tabs swipe as well as tap. The loading spinner, error and per-tab "No results" centre in the area below the bar and tabs, and the top scrim holds the background down to the tab row's bottom edge so rows dissolve into the tabs as they scroll under. Artists are ordinary rows now (circular art, name, "Artist") and page like everything else. The first page is still a single request for all three types at once, so the chooser is instant from the moment results land; every page after that fetches only the type you're looking at, at that type's own position in the results, so one tab running out no longer drags the others along. Switching tabs mid-fetch is safe — a page already in flight lands in the list it was fetched for. Each tab gets its own "Couldn't load more — tap to retry" row and its own "No results for …" message. The Search endpoint caps a page at 10 per type, so paging is what makes anything past the first ten reachable at all; appends de-dupe by id (offset paging over a relevance-ranked set genuinely repeats, and a duplicate key is a hard crash in a lazy list), a page that brings back nothing new ends that type's paging, and a failed page parks only its own tab behind the retry row instead of replacing the results with a full-screen error. The dead Playlists section went with the rest (the API never gets asked for playlists — it returns no track contents for playlists you don't own), along with the last hardcoded English headings on the screen.
- **The floating mini player is now on the Stats and Search screens.** Both lacked it, so starting a track from your listening stats — or from a search result — meant navigating back to reach transport controls. Both screens now carry the same mini player (and, on a wide screen, the pop-out player panel) as the Library, Album and Artist screens, including the album-art morph into the full player and the Queue button. On Stats and Search the bar stays full-width at every width, since neither screen has a two-pane right pane for the usual right-aligned placement to line up with; on Search it also rides **above the keyboard** — that screen auto-focuses its field, so a bar left at the window bottom would have spent most of its life hidden behind the keyboard. Opening the pop-out panel on a wide screen dismisses the keyboard first, so on Search the panel's seek bar, transport row and action row are reachable rather than sitting under the IME (closing the panel leaves the field unfocused — tap it to resume typing). On the unfolded screen, back closes the pop-out panel before anything the hosted screen would do with it, so it can no longer silently clear a Library multi-select behind the panel's scrim. On a ≥1200dp tablet-landscape window, where the mini player gives way to the docked full-player pane, that pane now shows on Stats and Search too.
- **Recent searches are editable, and remember twice as much** — the Search screen's Recent list keeps **10** entries instead of 5, each row has a trailing **✕** that drops just that entry, and a **Clear all** at the end of the list empties it. Both write straight through to `recent_searches.json`. The list now scrolls too, with a `max(IME, nav bar)` bottom inset outside the scroll container — ten rows plus the header plus Clear all is taller than the folded outer screen and any landscape geometry, and because Clear all sits at the *end* it would otherwise have been the first thing to go out of reach. The viewport stops above the keyboard rather than running behind it, which matters because the screen auto-focuses: the keyboard is up by default there.
- **Visualizer in the pop-out player panel** — the wide-screen pop-out player now carries the **circle** visualizer, blooming around its album art exactly like the full player: the art shrinks slightly and the ring reacts around it. It first shipped as a bottom wave, which turned out to be redundant — the browse screen underneath already draws one a few dp below the card's bottom edge, so the panel's copy just read as a second wave. It uses the *same* single `Visualizer(0)` instance the full player does (capture is gated app-wide in `PlayerViewModel` on playing + enabled, so there was no lifecycle handoff to build), and because the panel's content is only composed while it is visible, the per-frame loop is gone the moment you close it. Your Settings resolution and gain apply unchanged — the circle spreads its bands around a perimeter, so the small-surface band cap the wave needed doesn't apply here. Follows Surfaces = Circle / Bottom / Both like every other surface (**Surfaces = Bottom now leaves the panel with no visualizer at all**, which is the point), and with `RECORD_AUDIO` denied it shows only the static disc rather than prompting. This clears the last outstanding visualizer item.
- **Podcasts** — Lyra can now follow, browse and play podcasts. The Library filter gains a fourth **Shows** segment listing your followed shows (fetched once per session, cached for instant paint), Search gains a fourth **Shows** tab that pages, retries and swipes exactly like the others, and recent searches remember shows. Tapping a show opens a new **show detail** screen in the same floating-controls style as Album and Artist: a square-art hero with the episode count, a follow heart (unified `me/library`, optimistic with revert, the Library list updates without a refresh), a description that expands on tap, and the full episode list newest-first, fifty at a time. Single-pane puts the hero over the list; unfolded puts the hero left and the episodes right. Tapping an episode plays it; the hero's Play plays the newest one. There is deliberately no shuffle (a feed has no meaningful shuffle) and no touch-and-hold menu on episodes (its rows are all track-specific). `open.spotify.com/show/…` links open in Lyra. Every player surface handles a podcast episode as the now-playing item — the full player, mini player, pop-out panel, queue, Now Playing notification and home-screen widget show the episode name as the title, the show name as the subtitle and the episode's art (falling back to the show's), with correct seek and duration; lyrics are never looked up for an episode, the like heart is hidden, add-to-playlist is disabled, and Share gives the episode's own link. Two things had to be fixed on the way that affect every user: **`GET me/player` was never asked for episodes** (its `additional_types` defaults to tracks only), so while a podcast played the API returned no item at all and the player showed "Nothing playing" over audible audio; and the **Queue screen discarded episodes** that the API had always been returning, through Lyra's own track-uri filter. Decided by a device-run API spike on the shipped token scopes (every leg passed, no new scope needed); the temporary spike itself, including the hidden long-press on the Settings version row, is gone.
- **Podcast episode rows show your listening progress** — an episode you have finished reads "*date* · **Played**" with a small check and no runtime (the runtime of an episode you have finished is the one number that tells you nothing); one you are part-way through reads "*date* · **42m left**" with a thin progress bar on the line below, filled to roughly where you are; and one you have never started still shows its duration. The remaining time is the same figure the row hands playback, so a row can never promise a resume point the player then ignores.
  - **It needs one new Spotify permission, and it switches itself on** — Lyra now asks for `user-read-playback-position`, the scope that exposes an episode's resume point. **Your current session keeps working untouched**: refreshing a token can never widen what it was granted, so the feature arrives the next time you connect (Settings → Disconnect Spotify → connect), where Spotify's consent screen will list one extra permission, *"Read your position in content you have played"*. That is this release asking for it, not a change on Spotify's side. Until then the show screen carries one quiet line above the first episode saying so, and it disappears by itself once a token carrying the scope is stored. Lyra records what the token endpoint says it actually granted rather than what it asked for, so the hint can never claim a permission you did not give.

### Changed
- **Toolchain and dependencies upgraded to current** — **AGP 9.2.1 → 9.4.0**, **Gradle 9.6.1 → 9.7.1**, **Kotlin 2.4.0 → 2.4.20**, **Compose BOM 2026.06.00 → 2026.08.00**, **Material3 `1.5.0-alpha22` → `1.5.0-alpha27`**, **Navigation Compose 2.9.8 → 2.10.0**, **OkHttp 5.4.0 → 5.5.0**, **Coil 3.5.0 → 3.6.2**, and **Glance `1.3.0-alpha01` → `1.3.0-alpha02`**. Two source changes were required: the Material3 alpha made the checkable `DropdownMenuItem` overload a hidden deprecation, so the player's Lyrics / Visualizer menu items moved to `CheckableDropdownMenuItem`; and Navigation 2.10.0 introduced the predictive-back regression fixed below. Note that the Gradle daemon now needs a real **JDK 21** on the command line (`gradle-daemon-jvm.properties` pins `toolchainVersion=21` and Gradle 9.x will not fall back to `JAVA_HOME`, while Android Studio's bundled JBR is JDK 25).
- **Player Queue / Share / Add bar is a real `ButtonGroup` again** — `PlayerScreen` and the pop-out `PlayerCardContent` were converted from the plain-`Row` connected-shape workaround back to a genuine M3 `ButtonGroup` (via `customItem` + `animateWidth`), so the inter-button press-squeeze is back. The crash that forced the workaround was the **empty-overflow measure path**, not the component: supplying a real `ButtonGroupDefaults.OverflowIndicator` means the negative-width `IllegalArgumentException` can't occur. Verified across fold rotation, folded and unfolded, with the player open.
- **Release signing is wired into the build** — `assembleRelease` now emits an already-signed APK; the separate manual `apksigner` step is gone. Credentials are read at build time from the gitignored `local.properties` and never reach the APK (verified: no property name, no passphrase bytes, no `buildConfigField`). If `local.properties` or the keystore is absent no signing config is registered and the build still succeeds *unsigned*, so a fresh clone keeps working. The long-standing note blaming `Properties.getProperty` and the toolchain versions was a **misdiagnosis**: in a Gradle Kotlin build script `java` resolves to the `JavaPluginExtension` accessor and shadows the package root, so `java.util.Properties` fails with `Unresolved reference 'util'` and every `getProperty` call then reports an unresolved reference as cascading fallout. Importing `java.util.Properties` and using a bare `Properties()` compiles fine — and almost certainly would have on the old toolchain too.
- **Hardcoded-string audit** — roughly 46 hardcoded UI strings (content descriptions, the Settings cache / disconnect dialogs, Library section titles, the search empty state, the NOW PLAYING labels) moved into `strings.xml`, and every "N tracks" subtitle is now plural-safe via `pluralStringResource` — which also fixes the pre-existing **"1 tracks"**.
- **`LibraryScreen.kt` split into six files** — the Library screen had grown to 1,957 lines holding the screen entry, both adaptive layouts, the predictive-back machinery, the browser pane, the detail pane and nine list/tile cards in one file. It is now `LibraryScreen.kt` (entry + the shared `libArtKey` / search-bar transform keys + the pull-to-refresh haptic + the refresh-error dialog), `LibrarySinglePaneLayout.kt` (the single pane and all of its `SeekableTransitionState` predictive-back machinery), `LibraryTwoPaneLayout.kt`, `LibraryBrowserPane.kt`, `LibraryCards.kt` (the playlist / album / artist / "For you" tiles) and `LibraryTrackListPane.kt` (the playlist detail, shared by single- and two-pane). A pure refactor: nothing renamed, no signature or visibility widened beyond `private` → `internal` where a symbol is now read from a sibling file, and every comment documenting a hard-won rule moved with its code. Verified by normalising and diffing the concatenation of the new files against the old one — the only difference is one added section banner. 19 imports that were already dead are gone as a side effect.
- **The search bar moved to Material 3's current `InputField` API** — Material3 `1.5.0-alpha27` deprecates *both* older `SearchBarDefaults.InputField` overloads (the `query`/`onQueryChange` one Lyra used, and the intermediate `TextFieldState` + `expanded`/`onExpandedChange` one), leaving only the `TextFieldState` + `SearchBarState` form. That makes this a real refactor rather than a rename: the field now owns its own text, and a `snapshotFlow` bridge feeds the ViewModel, so the existing 400 ms debounce, blank-query filter and stale-response guard are all unchanged. The bar looks and behaves identically — same stadium `surfaceContainerHigh` Surface at 56 dp, same back-arrow leading icon and clear ✕, same transparent field container, same IME **Search** action — and the `"search-bar"` shared-bounds element still sits on the Surface, so the Library FAB→bar container transform is untouched. Two things the migration forced: the Recent list is now gated on the **field's** text rather than the ViewModel's (which is a frame or two downstream through the debounce, and would otherwise flash the Recent list back over the results on the first keystroke of a re-type); and because the current overload *requires* a `SearchBarState` and expands it on focus, on click and on the first keystroke — while Lyra composes no full-screen search bar for it to expand into — that state is created already **Expanded** and never touched. Collapsed would have made the field recompose every frame for the length of a slow spatial spring on focus, kept a `snapshotFlow` collector alive for the life of the screen, and armed a clear-focus-on-collapse effect, all for an expansion nothing renders. The Recent-list gate reads a derived Boolean rather than the field's text directly, so dragging the cursor or selection handle, or gesture-typing, no longer recomposes the results list.
- **The other two deprecation groups from the dependency bump are cleared** — every `ListItem(headlineContent = …)` (14 sites across Settings, Search, the song menu, the device picker, the add-to-playlist sheet, Album and Artist) is on the overload where the headline is the trailing `content` lambda, and the four `currentWindowAdaptiveInfo()` reads are `currentWindowAdaptiveInfoV2()`. Neither changes what you see: the adaptive-info swap is bit-identical for the 600dp check (V2 only adds 1200/1600 width buckets, and it still has no height buckets, so the measured-width docked-pane gate stays), and each `ListItem` edit moved exactly one block so no slot could be swapped. The new `ListItem` is a different, token-driven layout — the gap between leading art and text tightens from 16 to 12dp and vertical padding shifts by ±2dp — and those small spacing changes were accepted rather than pinned back. With the search bar done too, the Kotlin compile is now warning-free.
- **The mini player is hosted once for the whole app** — it (and, on unfolded screens, the pop-out player panel) used to be mounted separately by each browse screen, so every Library ↔ Search ↔ Album ↔ Artist ↔ Show ↔ Stats navigation slid the bar away and back. One host now wraps the whole navigation graph: the bar stays put while the screens slide underneath it, hides only on the full player, the queue, Settings and sign-in, and on an unfolded screen resizes in place between its full-width form (Search, Stats) and its right-pane form instead of leaving the screen. The pop-out panel is hidden and restored, rather than closed, when you open the full player or Settings. A predictive-back gesture out of the full player now brings the bar in with your finger, and the album art morphs with it, exactly as it did when the bar lived inside the Library.
- **Material 3 app bars replace the floating pills — everywhere** — the OneUI-style floating title and action pills, and the 300dp title bands they sat over, are gone from every screen. Each screen now has a real top app bar in the page's own colour:
  - **Library, Your stats, Settings and Queue** get a **large title bar that compresses to a small one as you scroll** and stays small until you are back at the top. The Library's is "Lyra" with a subtitle built from your counts (the playlist half is the number Spotify itself reports, not the number of rows loaded); Insights and Settings are actions in it. On a pane under 600dp tall — the folded outer screen in landscape — all four show a small pinned bar instead, because 120–152dp of title plus a tab row would eat over half the screen before a single row. Stats, Settings and Queue lose their 300dp title bands entirely, so the range picker, the first setting and the first queued track are visible immediately.
  - **The Library's Playlists / Albums / Artists / Shows filter is a pinned tab row** instead of the connected buttons, which is also what finally fixed the truncating labels that started this ("Playl…", "Albu…") — and the four lists are now **swipeable pages**: swipe sideways between tabs as well as tapping them, with each tab keeping its own scroll position, restored when you come back to it (across opening a playlist, navigating away and folding/unfolding).
  - **Album, artist, podcast-show and playlist / Liked Songs detail** get one bar over the hero — back, the heart, share, ⋮ — with the title **handing into the bar over roughly the distance the big hero title itself takes to slide under it**, using Material 3's own hand-off easing. It tracks your finger, so it fades back out as you scroll up. Two-pane and the loading / error states get the same bar (the left card's carries no title, since the hero's own name sits right under it).
  - **Library multi-select is a standard contextual app bar** (close / "N selected" / remove) in that same slot, with the same confirm-on-2-or-more dialog and the same disabled states as the old floating selection pill.
  - **Search is the one screen with no app bar** (its search field *is* the top element, and Material 3 says not to transform a bar into a search bar) and the full player stays immersive, as it always was. The Library search FAB is still a FAB, and its FAB→search-bar morph is untouched.
- **Where the mini player sits over an open keyboard** — with the keyboard up the bar now floats a navigation-bar height *above* it instead of resting flush on it, so Search's bottom visualizer wave stays visible in that strip exactly as it is at rest under the bar. Nothing moves on any screen with the keyboard down.

- **Dead Spotify model fields** — dropped `popularity` (artist and album), the user profile's `product` field, and the dead `ArtistTopTracksResponse` model — all gone from or irrelevant to Spotify's Feb-2026 Web API response shape and unread anywhere in the app.

### Fixed
- **Playlist track counts now come from the server, not from three different local guesses** — after removing several songs from a playlist, the detail hero's "N songs" and the Library card's count could disagree with each other and with Spotify, and only re-opening the playlist or pulling to refresh put them right. The counts were being maintained by three independent writers with three different arithmetics — the removal's row delta, the cache's metadata decrement, and the cache-change re-read that lands last — and none of them ever asked the server. They agree only while the rendered rows, the cached rows and Spotify's own playlist metadata all match, and they do **not** match for any playlist holding items Lyra filters out of the list (unplayable tracks, local files, episodes), so removing *k* songs dropped the hero by *k* plus the size of that gap while the card dropped by the correct *k*. There is now one rule and one writer: every in-app change — the multi-select batch removal (whole or partial), the song menu's "Remove from this playlist", and adds or removes through the add-to-playlist picker on any screen, including the player's — keeps its instant optimistic edit and then re-reads the playlist's authoritative total once, writing it to the hero, to the playlist metadata behind the browser and two-pane-left cards, and to the disk cache in a single update. The re-read is debounced so a burst of edits costs one request, it is per playlist so an edit to one can't cancel another's, and it deliberately waits a beat because a `GET` issued the instant after a `DELETE` can still answer with the pre-removal total. Pull-to-refresh inside a playlist now heals the browser card too, instead of only the hero.
- **Paging past page 0 right after a removal could duplicate rows, and reset the count** — scrolling a >100-track playlist on after a batch removal appended songs the list already had; selecting one of the twins selected both, and removing it then dropped two rows for one song, which is how the numbers ended up moving around. The page that arrives moments after a removal can still be served from Spotify's **pre-removal** list, so it starts inside rows already on screen — one duplicate per song removed above that point — and it carries the pre-removal `total`, which undid the correct count. Pages are now de-duped against the loaded list by uri — but only for a playlist you have edited in-app this session, since that stale-page window is the only way a repeat can be an artefact; a playlist that genuinely holds the same track twice (Spotify's own client allows it behind an "already added" prompt) still shows both rows — the paging offset advances by the raw page size minus any overlap dropped, and a page's `total` is ignored while that playlist's authoritative re-read is still pending. The cache-change re-read also no longer assigns the filtered row count to the paging offset, which was a second, independent way to re-fetch an overlap.
- **Search no longer hides under the side navigation bar in landscape** — in folded landscape with 3-button navigation the nav bar sits on the left or right edge, and only the results list cleared it. The search field, the Recent rows (including the ✕ buttons, which landed right under the nav buttons) and the recents column had no horizontal inset at all and ran straight underneath. The whole screen now takes one horizontal inset — nav bar *and* display cutout — at its outermost container, so the bar, the new type chooser, all three result lists and the recents all clear it. Portrait is unchanged, and the mini player, which already handled its own, is untouched.
- **The search FAB↔bar morph stayed bar-shaped and then snapped to the full cookie** — on a slow predictive-back drag the container kept the stadium outline until near the bottom of the gesture; on a normal back the SoftBurst appeared abruptly before the gesture even finished. Two causes compounded. `sharedBounds` interpolates **bounds** and cross-fades the two **contents** — nothing in it morphs the silhouette, so each end simply kept drawing its own shape. And the default `resizeMode` draws the *entering* FAB scaled to the bar's width — roughly 4.75× on a phone — so the SoftBurst was a ~380dp blob centred on a 56dp-tall box, spilling far outside the bounds with only the fade hiding it; that overspill is what made the cookie "appear full" early. Both are fixed by a `clipInOverlayDuringTransition` clip that cuts the shared content, in the shared-element overlay where it already renders, to a graphics-shapes **`Morph`** between `MaterialShapes.SoftBurst` and a true stadium. It only *clips* — nothing is filled or stroked, which is what sank the earlier square→cookie attempt on the Library hero. The clip gets no progress value, so the fraction is derived from the animated bounds themselves (`t = (80dp − height) / (80dp − 56dp)` is exact, because the bounds animate with one eased fraction), which means the clip needs no direction handling and **seeks with predictive back for free**. Nothing new is animated.

Known and left alone: the search FAB's drop shadow still reappears in one frame as the morph settles, because the outline clip necessarily clips the shadow's blur.

- **Back navigation was inconsistent, and the previous screen stayed touchable after it looked gone** — three distinct bugs, all of which presented as "back feels broken".
  - **Predictive back stopped using the app's own transitions.** Navigation 2.10.0 added `predictivePopEnterTransition` / `predictivePopExitTransition` to `NavHost`, and they do **not** inherit from `popEnter`/`popExit` — they fall back to `DefaultNavTransitions`, whose predictive pop-exit is `scaleOut(targetScale = 0.7f)` with no paired fade. On 2.9.8 a predictive gesture seeked `popExitTransition`, so this had always worked; after the bump every gesture back silently became shrink-and-stall while the build stayed green and lint stayed clean. Because `enableOnBackInvokedCallback` is on, button backs dispatch through the same machinery, so both paths broke and appeared to alternate at random. All six transitions are now passed explicitly.
  - **The outgoing screen kept catching touches for up to a second.** A shared element's bounds animation is created as a **child** of the enclosing transition, and a parent `Transition` never reaches `currentState == targetState` until every child finishes — which is exactly when Navigation disposes the outgoing `NavBackStackEntry`. During a pop it also z-orders that entry **above** the incoming screen, and in Compose **alpha does not affect hit testing**. The bounds morphs were fed `motionScheme.defaultSpatialSpec()`, which under `MaterialExpressiveTheme` is *underdamped* (damping 0.8 / stiffness 380) and oscillates ~600 ms–1 s, so the slide and fade finished while the nav transition ran on, leaving an invisible but fully touchable copy of the previous screen on top. Since `MiniPlayer` registers the `"album-art"` shared element in the **nav** scope on narrow screens and the mini player is on every screen, this hit *every* navigation — including ones with no visible morph, such as Settings → Library. Every content-swapping transition now shares one finite spec, `screenTransitionSpec()` (a plain `tween(300, FastOutSlowInEasing)` — platform defaults, no hand-rolled curve): the nav slide *and* its paired fade (bare `fadeIn`/`fadeOut` default to a **spring**, which is what desynced them), the shared-element bounds morph, the Library browser↔detail swap, the two-pane right-pane swap, the pop-out panel, the mini player, and the Settings expand/collapse. Everything now lands on the same frame, so the entry is disposed the instant the motion stops — and finite specs also seek cleanly under predictive back. Springs are kept for pure value animations that can't hold content alive (art settle on track change, `artScale`, the Library FAB padding).

The full-screen scrim therefore ate every tap meant for the library for the full 300 ms fade, despite being ~4% opacity by 250 ms. The tap-to-dismiss modifier is now installed only while the panel is open, so the fading `Box` carries no pointer input at all.

The mini player used `thumbnailUrl`, which is Spotify's **smallest** image (`images.last()` — 64 px), while the player uses `artUrl` (`images.first()` — 640 px); during a morph Compose renders *one* participant across the animating bounds, and on a pop the target is the mini player, so a 64 px bitmap was being upscaled roughly 10×. Coil also sizes its decode to the composable's own box, 44 dp here, so even the full-size URL would have decoded too small to survive the morph. The mini player now requests the full-size URL at its natural size; the cost is one bitmap for the currently-playing track, which the full player loads anyway.

Fixing it took three rounds and the first two diagnoses were wrong. (1) `isFollowed` was only ever left non-null on the success path, so any failure — or an empty `me/library/contains` response — kept the button disabled forever; it now seeds from the cached `followedArtists` list first and falls back to `false` with a logged warning, so the heart is always enabled and the first toggle corrects the state either way. (3) The live February-2026 docs show `PUT`/`DELETE me/following` are **removed for dev-mode apps** (a plain 403 "Forbidden" regardless of scopes — confirmed in device logcat), replaced by the unified `me/library` with artist uris. `me/library` enforces **per-entity scopes**, so the original artist-uri failures — *and* the Artists filter looking empty, because its `GET me/following` was 403ing too — were the missing **`user-follow-read`** / **`user-follow-modify`** scopes all along. Those are now in `SCOPES`, the toggle and status check are back on `me/library`, and the dead write endpoints are deleted. **Existing installs need one disconnect + reconnect** so the token carries the new scopes. The lesson: a plain `403 Forbidden` means the endpoint is gone for your app tier, while `403 Insufficient client scope` means it's a scope problem — check the migration guide and the per-entity scopes *before* building.

Two rounds. Titles now reserve two lines and the subtitle line always renders, making every tile the same height.

Discovered from an on-device DropBox crash record.

## [3.1.2] - 2026-06-18

_A compliance + polish release — Lyra now gracefully re-authenticates when a Spotify refresh token expires (ahead of Spotify's new six-month token-expiration policy taking effect 2026-07-20), and the app icon now appears, crisply, on the sign-in screen._

### Added
- **Automatic re-authentication when a Spotify refresh token expires** — Spotify is making refresh tokens expire **6 months after the original authorization** (rolling out to existing apps on **2026-07-20**); a dead refresh token now returns `invalid_grant` instead of a new access token. Lyra previously had no handling for this: the failed refresh was silently ignored, the dead token was never discarded, and `isAuthenticated()` stayed `true` — so the user would have been stranded on Library with every Web-API call 401-ing, unable to get back to sign-in. Now, when a refresh fails with `invalid_grant`, `SpotifyAuthManager.refreshAccessToken()` **discards the stored tokens** and emits a one-shot `sessionExpired` event; `LyraNavGraph` observes it and routes the user back to the **sign-in screen**, which shows a *"Your Spotify session expired"* notice. The Client ID is preserved, so reconnecting is a single **Connect** tap. The discard is gated specifically on AppAuth's `invalid_grant` (`TYPE_OAUTH_TOKEN_ERROR` + `INVALID_GRANT`) — **transient/offline refresh failures never sign the user out**. Per Spotify's guidance, a failed refresh is **never retried**: `TokenManager`'s 401 path now refreshes-and-retries only on success, dedups concurrent 401s by token identity (so a server-side-revoked-but-locally-valid token still triggers the refresh that surfaces `invalid_grant`), and returns the original 401 untouched when the refresh fails. App Remote playback control is unaffected — it authenticates through the installed Spotify app, not Lyra's refresh token.
- **App icon on the sign-in screen** — the Lyra icon now sits above the title on the auth screen (both first launch and the session-expired screen), using the same rounded-tile treatment as Settings → About.

### Fixed
- **App icon no longer looks blurry** — the app-icon tile on Settings → About (and the new sign-in-screen icon) was rendered with `Modifier.scale(1.5f)`, which magnified a small rasterised copy of the vector drawable and softened it. ### Fixed
- **Player top-bar elements and lyrics went unreadable on some covers** — a regression from the edge-sampling background change above. The player background gradient was repointed from the Palette **Vibrant** colour to the art's **edge** colour, but the top-bar controls (chevron / NOW PLAYING / full-screen / options, in both the full player and the pop-out panel) kept deriving their black-vs-white tint from the **dominant accent** — so on a cover with a bright accent but dark edges (or vice-versa) they contrasted the wrong colour and vanished into the background (black-on-near-black). Those elements now choose black/white against the *actual* top background (the edge gradient composited over the surface) via a dedicated `topContentColor`; the Play/pause cookie keeps `onAccentColor` since it's genuinely filled with the accent. The **lyrics** had the same issue when the **circle visualizer is off**: with no contrasting blob behind them they sat directly on the dark gradient, so the accent-derived colour could disappear — lyrics now fall back to the theme's `onSurface` when no circle is shown, and keep `onAccentColor` (unchanged) when the visualizer blob is behind them.
- **Liked Songs duplicated tracks at every page boundary** — scrolling Liked Songs past a 50-track page could repeat a block of songs across the boundary (sometimes one, sometimes several), and could skip songs; long playlists were unaffected. Spotify's `me/tracks` `offset` indexes *every* saved item, but `SavedTrack.track` is null for songs removed from Spotify, and every Liked-Songs path dropped those with `.mapNotNull { it.track }` and then advanced the next offset by the **post-filter** size — so any page containing a removed track shorted the offset and the next page re-fetched the overlap (block size = number of removed items in that page). The background liked-songs fetcher baked the same drift into the on-disk cache (and, because the stored count can never reach the raw total once any track is removed, polled the tail forever). Regular playlists were immune because `loadMorePlaylistTracks` already advanced by the **raw** `resp.items.size`. Fixed by advancing every Liked-Songs offset by the raw page size (matching the playlist path), de-duplicating each append by track id as a safety net (liked songs are unique by id; playlists, which may legitimately repeat a track, are untouched), and **self-healing the existing corrupted cache on next open** of Liked Songs (the cached list is de-duped and re-persisted — no clear-storage needed). The fetcher now tracks a raw offset across iterations with a real end condition and re-seeds if the cache is reset under it; `playFromLikedSongs` de-dupes the play queue for the same reason.
- **Playlist tracks duplicated when reopening a playlist** — opening a playlist repeatedly could double its track list (10 → 20 → 30 …), the header flashing the doubled total before settling back. The `TrackList` auto-fires `onLoadMore` the instant a short list "reaches bottom", which raced `selectPlaylist`'s async cache load: `loadMore` fetched page 0 and appended it onto the just-loaded cached list, then **persisted** the doubled list, so it compounded on every open (a pull-to-refresh reset it). Exposed by the track-count fix above — before it, the initial `total` was 0 so `canLoadMore` was false during that window and the race couldn't fire. `loadMorePlaylistTracks`/`loadMoreLikedSongs` now bail while `isLoadingTracks` is true, so pagination can't fire until the initial load settles; legitimate scroll-to-load is unaffected.
- **Playlist track count drifted after an in-app add/remove** — adding/removing a track in-app updated the cached track list but not the library's `/me/playlists` metadata count, so the My Playlists card (left pane) and the detail header (right pane) disagreed until a full library refresh — and Spotify's playlist-metadata count is itself eventually-consistent (it lags the real total for a while, so even a refresh could briefly show the old number). The surgical cache methods (`appendToPlaylistTrackList`/`removeFromPlaylistTrackList`) now also mirror the metadata count to the new cached size — an **absolute** value, never a ±1 delta that would compound existing drift — and ping the cache revision so the My Playlists list re-syncs; both panes update instantly on an in-app change. On open, a lightweight `limit=1` reconcile heals any remaining drift and picks up changes made on other devices, using `maxOf(serverTotal, loadedCount)` so a lagging server total can never drag the count below what's actually loaded. The **"Remove from this playlist"** action was also routed through that same single cache method — it previously hand-rolled its own `saveTrackList`, which skipped the count sync and left the cache one short of the metadata, silently no-op'ing the *next* add.
- **Stale auto-generated mosaic hid Spotify's real playlist cover** — a playlist created with no Spotify art gets a local 2×2 mosaic, but once Spotify generated a real cover the mosaic kept winning forever, because `PlaylistCard` and the detail header preferred the mosaic file over `playlist.thumbnailUrl`. Flipped the priority: Spotify's `thumbnailUrl` is shown when present, with the mosaic as a fallback only when Spotify has no art yet — so a brand-new playlist still gets the instant local mosaic, then switches to Spotify's cover once it exists and the library is refreshed.
- **Playlist track counts were always 0 (Spotify renamed the field)** — every playlist in the library list showed the owner's name instead of a track count, and the detail header briefly showed the wrong number, because `GET /me/playlists` now returns the per-playlist count under `"items": {href, total}` instead of the old `"tracks"` key — so `SpotifyPlaylist.tracksMeta` never parsed and `trackCount` was always 0. Mapped `@SerializedName(value = "items", alternate = ["tracks"])` (legacy `tracks` kept as a fallback). Now the list shows real counts — **My Playlists** shows count-only (you're the owner) and **Following** shows **"Owner · N tracks"** — and the detail header shows the correct total from the first frame. (A lightweight per-open `limit=1` reconcile was later re-added — see "Playlist track count drifted after an in-app add/remove" below — to heal drift from in-app edits and changes made on other devices.)
- **No toasts while the pop-out player panel was open** — add-to-playlist results, device-transfer failures, and player errors are shown as Android `Toast`s, but the toast effects lived only in `PlayerScreen` (the full player, used on narrow screens). On wide / unfolded screens the pop-out `PlayerCardContent` is shown *instead of* it and had no toast logic, so any action taken from the panel produced no toast. Mirrored the three toast effects into `PlayerCardContent` (they're mutually exclusive with the full player in steady state, so nothing double-toasts).
- **Search screen slid under the side navigation bar in landscape** — the search bar and results applied no horizontal window insets, so in landscape (nav bar on the side, e.g. folded) the back button / text field and result rows ran underneath it. Added `WindowInsets.navigationBars.only(WindowInsetsSides.Horizontal)` padding to the top bar and content, matching every other screen; portrait is unchanged (zero horizontal inset there).
- **New playlist didn't appear in the library until pull-to-refresh** — creating a playlist from the song touch-and-hold menu or the player's add-to-playlist sheet wrote it to the cache but not the in-memory list the browser renders, so it stayed hidden until a manual refresh. `LibraryCache` now exposes a revision `StateFlow` (bumped on `prependPlaylist`/`removePlaylist`, never on a plain save) that `LibraryViewModel` collects to re-sync its playlist list from the cache — the new playlist shows at the top immediately, no matter which screen created it.
- **Adding/removing a song to an owned playlist didn't show until pull-to-refresh** — opening the playlist served a cached track list whose snapshot still matched the (equally stale) library metadata, hiding the change. Add/remove now **surgically** update the cached track list (append to the end / filter the row out, keeping the snapshot id — same idea as Liked Songs) so re-opening reflects it with no refetch. A new `LibraryCache.trackListChanges` signal additionally **live-refreshes the playlist while it's open**, covering every entry point: the song menu, the full player, the pop-out panel, and album detail (album rows now carry a reconstructed full track so they refresh too). To protect lazy-loading, the surgical append is skipped when a playlist's cache is only partially paged (the new track loads on scroll instead) — splicing into a partial prefix would duplicate or misorder rows.
- **Device picker sheet opened then collapsed** — the `DevicePickerSheet` briefly opened expanded, then settled into its half-height partial detent a moment later, clipping off the bottom of the device list (and the volume control beneath it) whenever the list just barely filled the partial height. It now opens fully expanded and stays there — the sheet state is restricted to Hidden↔Expanded (no partial detent) via the non-deprecated `rememberBottomSheetState`.
- **Playlist track lists capped at 50 / wrong count** — opening a playlist only ever loaded the first 50 tracks with no way to see the rest; now they lazy-load on scroll exactly like Liked Songs (`LibraryViewModel.loadMorePlaylistTracks` + `playlistTracksOffset`/`playlistTracksTotal`, wired through `TrackList`'s existing `canLoadMore`/`onLoadMore`). The page offset advances by the **raw** page size (not the playable-filtered count) so playlists with unavailable tracks don't re-fetch or duplicate rows; pull-to-refresh resets paging cleanly. The detail-header track count now reads the authoritative `playlistTracksTotal` instead of the loaded-track count, so it shows the real total immediately instead of "50" until you scroll to the bottom.
- **Visualizer didn't react over Bluetooth headphones** — a `Visualizer` binds to the audio output route that was active when it was created, and returns silence once the route changes (e.g. speaker → Bluetooth A2DP); since `VisualizerManager` created the instance once and never re-bound it, switching to BT mid-session (or having it connected after the instance was made) left the visualizer flat — yet enabling it *fresh* while already on BT worked, which ruled out the platform A2DP-offload limitation and pinned it on the stale instance. `VisualizerManager` now registers an `AudioDeviceCallback` and re-creates the capture when the output device set changes (debounced 400 ms so the new route settles first), and a `routeDirty` flag recreates on the next `start()` if the route changed while paused. Re-binds correctly across speaker↔Bluetooth in both directions.
- **Visualizer kept moving on quiet/silent audio; was also volume-dependent** — the `Visualizer` ran in its default `SCALING_MODE_NORMALIZED`, which auto-gains every frame so the loudest bin sits at full scale; on a quiet or audibly silent track this amplified the noise floor into constant motion (and defeated the silence gate, which never saw a low value). Reworked the gain pipeline to mirror how ProjectM/Milkdrop behave: the capture now runs in `SCALING_MODE_AS_PLAYED` (raw magnitudes track the true output level, so silence reads ~0 — measured exactly `0.0` when paused), and a new `Agc` (automatic gain control, one instance per painter) normalizes each frame against a slowly-released rolling peak so the visualizer looks equally lively at any volume (100% vs Samsung's 150% both converge to the same amplitude) instead of being dead when quiet. A smoothstep soft-gate keyed on the *true* level keeps genuine silence flat — because the gate runs on the raw AS_PLAYED magnitudes, the AGC can never amplify the noise floor back into motion. Beat detection stays on the raw (volume-invariant) magnitudes. Thresholds were set from on-device measurement of the actual magnitude scale (silence `0.0`, quiet ≈ `6–34`, loud ≈ `80–168`) at the device's 10 Hz FFT rate.
- **Folded-landscape player rotation crash** — rotating to landscape on the full player crashed with `IllegalArgumentException: maxWidth must be >= minWidth` from Material 3's `ButtonGroupMeasurePolicy`: the Queue/Share/Add action bar used an M3 `ButtonGroup` with overflow disabled (empty `overflowIndicator`/`menuContent`), and its overflow measure computes a negative width when the controls column is tight. Replaced both the full-player and pop-out-panel button groups with a plain `Row` of the same connected-shape (`ButtonGroupDefaults.connected*ButtonShape`) tonal icon buttons — identical at rest, but a `Row` clips instead of producing inverted constraints. (Trade-off: loses the ButtonGroup interactive press-squeeze; the overflow feature was unused.)
- **Album-art morph was one-directional into the player** — opening the full player from a detail page (Album/Artist) morphed the art into the mini player, but navigating *back* did not morph it home. Two causes: on **narrow** screens the mini player registered the `"album-art"` shared element twice in the nav scope (primary + secondary both resolving to the nav scope), which resolved ambiguously and broke the morph on pop; on **wide** screens the secondary nav scope was gated on `transition.isRunning`, which never catches the exiting element on a back/pop (a shared element added after a pop begins is too late to be the exit participant). Fixed by registering the mini's nav scope once on narrow, and *continuously while the pop-out panel is fully closed* on wide (driven by the panel's own `Transition` so it can't desync from the panel slide) — so the element exists before any pop starts. Morphs both directions now in folded portrait, folded landscape, and unfolded.
- **Album art popping in late on track change (full player & pop-out panel)** — the art container slid into place before its image had loaded, so on a cold (non-memory-cached) image the art would appear partway through the slide or just snap in at center. The art now loads through a `crossfade(200)` request: Coil skips the crossfade on memory-cache hits (already-loaded art still shows instantly) and fades cold art up instead of popping. The request is `remember`ed on the art URL so the per-second progress tick doesn't rebuild it; the slide/shared-element animation code is unchanged.
- **Settings screen missing bottom fade scrim** — `SettingsScreen` had `navigationBarsPadding()` applied directly to the scrollable `Column` with no `Box` wrapper, so there was no overlay surface for the scrim; restructured to wrap in a `Box`, removed `navigationBarsPadding()` from the `Column`, added a matching bottom `Spacer(scrimHeight)`, and overlaid the `Brush.verticalGradient` scrim `Box` at `Alignment.BottomCenter`, consistent with all other scrollable screens
- **Bottom visualizer clipped to right pane on Album Detail and Artist Detail wide screens** — `FftWaveCanvas` was placed inside the right card's `Box`, so it only covered 58% of the screen width; moved to an outer `Box` wrapping the full `Row` so it spans both panes at full width, matching the Library screen layout; right-card scrim now fades to `surface` instead of `background` to match the Card's background color
- **Shuffle and repeat buttons misaligned with skip buttons** — the dot indicator was placed in a `Column` below the `IconButton`, making the Column's layout height 53dp (48dp button + 5dp dot) vs the 48dp skip buttons; the Row's `verticalAlignment = Alignment.CenterVertically` was centering the Column's midpoint instead of the icon's midpoint, pushing shuffle/repeat ~2.5dp too high; fixed by wrapping in a `Box` instead — the dot overlays with `align(Alignment.BottomCenter).offset(y = (-5).dp)` outside the layout flow so the Box reports 48dp height, matching the skip buttons; applies to both `PlayerScreen` and `PlayerCardContent`

- **Like/unlike** from the player now surgically updates the liked-songs cache (prepend on like, remove on unlike) without invalidating or re-fetching the full list; external likes/unlikes are detected by count diff on next library open — new songs prepended in one API call, removed songs trigger a full refetch
- **Sleep timer Live notification** on Android 16+ devices — when a sleep timer is active, a separate pinned notification appears in the Live notifications section showing a live countdown and a Cancel button; on Samsung OneUI 8, requires enabling "Live notifications for all apps" in Developer options (a Samsung limitation)
- **Settings → Notifications** section (Android 16+ only) — shows whether Live notifications are enabled for Lyra; on Samsung, tapping Enable opens an explanatory dialog with a direct link to Developer options

### Changed
- **Pull-to-refresh** on liked songs now preserves background-fetch progress beyond page 1 instead of overwriting the full cache with only 50 tracks

### Fixed
- **Album track count** now reads "1 song" instead of "1 songs"
- **Playlist thumbnails** not showing in the library browser — Spotify's thumbnail URL was available on every playlist object but `PlaylistCard` and `PlaylistListCard` only ever rendered a mosaic or a blank icon; both now fall back to the Spotify thumbnail when no mosaic exists, with mosaic generation skipped entirely for playlists that already have Spotify art
- **Queue screen crash** when shuffle is on with a small playlist — Spotify's queue API repeats the same track multiple times in the response; duplicates are now filtered out before display
- **Shuffle and repeat** active state now shows a small dot indicator below the button (both full player and pop-out panel), matching Spotify's own affordance; the previous color-only tint was hard to read against many album art colors
- **Launch crash** after adding `albumType` field to `SpotifyAlbum` — Gson bypasses Kotlin non-null defaults on deserialization, leaving the field `null` on cached tracks and crashing `hashCode()`; fixed by making the field nullable
